# 5. Поток данных и пайплайн

## 5.1. Полный поток

```text
HOST
  mesh / shape
      │  (host slicing: mesh ∩ planes)
      ▼
  3D-полилинии среза
      │  adapter: построить CoordinateFrame, 3D → 2D
      ▼
  Slice[] (2D, mm)  ──────────────┐
      │                           │
      │  adapter: собрать          │
      │  ProcessingRequest         │
      ▼                           │
  ENGINE                          │
   validate                       │
   normalize (встроенный)         │
   operation[0..n]                │
   final validate                 │
      │                           │
      ▼                           │
  ProcessingResult ───────────────┘
      │  adapter: 2D → 3D, проверка round-trip
      ▼
  HOST: визуализация / экспорт / сборка
```

### Почему 2D

Каждый срез лежит в своей плоскости. Если обрабатывать его в мировых 3D-
координатах, любой алгоритм (сглаживание, кривизна, филет) должен учитывать
ориентацию. Перевод в локальный кадр убирает эту сложность: движок всегда
работает с `(x, y)`, а кадр хранит адаптер. Это же позволяет обрабатывать
радиальные и наклонные срезы тем же кодом.

### Проверка round-trip

Адаптер после подготовки и после получения результата проверяет:

```text
max |to_3d(to_2d(p)) - p| <= 1e-6 * scale
```

где `scale` — характерный размер модели. Если проверка не проходит, это
`E_FRAME`, а не ошибка движка: кадр построен неверно или потерял точность.

## 5.2. Стадии раннера

```text
request
  │
  ├─ 1. schema/version/limits/params        (validation)
  ├─ 2. target expansion                   (selection)
  ├─ 3. normalize                          (built-in)
  ├─ 4. operations[]                       (user pipeline)
  ├─ 5. final validate                     (built-in)
  └─ 6. metrics/diagnostics assembly
```

`normalize` и `final validate` нельзя отключить в v1. Это гарантирует, что
методы получают предсказуемые данные, а экспорт — валидную геометрию.

Порядок операций по умолчанию (рекомендация, не жёсткое правило):

```text
normalize
  → repair (если нужен)
  → fillet_corners
  → smooth
  → simplify
  → optimize_curve (если включён; после simplify, чтобы упрощение не
    заострило уже скруглённые гибы)
  → densify
  → limit_curvature (если включён)
  → final validate
```

`densify` стоит последним, потому что он задаёт выходную плотность. Если
`simplify` идёт после `densify`, он может снова проредить точки — это допустимо,
но тогда `densify` теряет смысл.

## 5.3. Normalize

Задачи:

1. Проверить конечность чисел, минимальное число точек, ненулевые длины.
2. Удалить подряд идущие дубликаты ближе `min_segment_mm` (по умолчанию
   `1e-4` мм).
3. Для `closed=True`: убрать повтор первой точки в конце, если он есть.
4. Для `closed=False`: не замыкать. Если концы ближе `close_tolerance_mm`
   (параметр `normalize`), замкнуть и пометить `closed=True` — только по
   явному разрешению.
5. Нормализовать ориентацию: внешние CCW, отверстия CW (если
   `options.normalize_winding`). Ориентация меняется заменой порядка точек;
   `segment_tags` переворачивается согласованно.
6. Определить вложенность, если `parent_id` не задан: even-odd / ray casting;
   для `CUT` внутренний контур получает `parent_id` внешнего.
7. Проверить, что `SCORE` с `fold` имеет корректный `angle_deg` и `direction`.

`normalize` не сглаживает и не меняет форму. Он только приводит данные к
инвариантам. Все изменения фиксируются в диагностике (`INFO`), чтобы адаптер
мог объяснить, почему число точек изменилось.

## 5.4. Resample

Передискретизация по длине дуги:

* `mode="uniform"`: шаг `spacing_mm`; последняя точка сохраняется, даже если
  шаг не делится нацело.
* `mode="adaptive"`: шаг зависит от кривизны:
  `spacing = clamp(chord_tolerance, base_spacing / (1 + k * curvature), min, max)`.
* Открытый контур: концы фиксированы.
* Замкнутый: начинать с исходной первой точки, чтобы результат был стабилен.
* `preserve_tags`: теги сегментов переносятся на новые сегменты по исходному
  диапазону; при попадании на границу выбирается тег сегмента, в котором лежит
  середина нового сегмента.

Сложность `O(n + m)`, где `m` — число выходных точек.

## 5.5. Simplify (Дуглас–Пекер)

* Точки, помеченные как якоря (`preserve_tags` или углы с
  `preserve_corners_deg`), не удаляются.
* Замкнутый контур: алгоритм запускается от двух самых удалённых точек, чтобы
  не зависеть от начала; либо контур разрезается в точке старта и обрабатывается
  как открытый, затем замыкается.
* `tolerance_mm` — максимальное расстояние от исходной точки до хорды.
* После упрощения проверяется, что осталось минимум 3/2 точки; иначе этап
  возвращает ошибку `E_GEOM_DEGENERATE`.

Сложность в среднем `O(n log n)`, в худшем `O(n²)` (например, спираль). Для
v1 этого достаточно; при больших контурах — итеративная реализация без
рекурсии, чтобы не упасть на глубокой рекурсии.

## 5.6. Smooth

Два алгоритма на выбор:

### Chaikin

Для каждого сегмента `(p_i, p_{i+1})` добавляются точки:

```text
q = 0.75 * p_i + 0.25 * p_{i+1}
r = 0.25 * p_i + 0.75 * p_{i+1}
```

Для замкнутого контура обрабатываются все сегменты; для открытого концы
фиксируются. Одна итерация удваивает число точек, поэтому после Chaikin нужен
`simplify`/`resample`.

Плюсы: простой, устойчивый, предсказуемый. Минусы: контур «сжимается»,
радиус на выпуклых углах меняется; жёсткие углы нужно сохранять заранее.

### Constrained Laplacian

```text
p_i' = p_i + λ * (0.5 * (p_{i-1} + p_{i+1}) - p_i)
```

* `λ` — вес (0..1), обычно 0.3–0.5.
* Якоря (`preserve_corners_deg`, `preserve_tags`) не двигаются.
* После каждой итерации проверяется `max_deviation_mm` от исходной позиции;
  если превышено — вес уменьшается или итерации прекращаются.
* Для замкнутого контура соседи замыкаются; для открытого концы фиксированы.

Плюсы: контроль отклонения. Минусы: может «сплющивать» мелкие детали; нужен
итеративный контроль.

В v1 по умолчанию `chaikin`, потому что он проще и детерминированнее. Оба
алгоритма должны сохранять `closed`, роли, теги и `parent_id`.

## 5.7. Fillet corners

Для каждого угла с turn-углом `φ` (внешний угол поворота, 0..π):

1. Если `φ < min_turn_deg` — угол не трогаем.
2. Радиус `r` из параметра. Максимально допустимый по соседним сегментам:

```text
r_max = min(len_prev, len_next) / 2 / tan(φ / 2)
```

(для `φ → 0` `tan` мал, `r_max` велик; для `φ → π` `tan` растёт, `r_max → 0`).

3. Если `r > r_max`:
   * `mode="clamp"` → `r = r_max`, `WARNING`;
   * `mode="error"` → `E_CONSTRAINT_UNSATISFIED`, контур/срез не меняется;
   * `mode="skip"` → угол остаётся острым, `INFO`.
4. Если `r < material.min_bend_radius_mm` → `E_CONSTRAINT_UNSATISFIED`
   (или `WARNING` в `clamp`, если политика разрешает).
5. Касательные точки:

```text
t = r * tan(φ / 2)
P_start = P_corner - t * dir_prev
P_end   = P_corner + t * dir_next
```

где `dir_prev`/`dir_next` — единичные направления сегментов к углу/от угла.
Центр дуги — пересечение нормалей на расстоянии `r` от обеих касательных.

6. Число сегментов дуги:

```text
n = ceil(φ / (2 * acos(clamp(1 - tol / r, -1, 1))))
```

где `tol` — `chord_tolerance_mm` (по умолчанию `0.05`). Ограничить
`1 <= n <= arc_segments_max` (например, 64). Если `tol >= r`, достаточно
одного сегмента.

7. Заменить угол на `[P_start, arc_points..., P_end]`.
8. Пометить новые сегменты тегом `arc` (если `include_point_tags`).

Ограничения:

* филет не должен пересекать соседние сегменты; проверка `r <= r_max` это
  гарантирует для простого угла, но при очень коротких сегментах нужно
  дополнительно проверять, что касательные точки не выходят за середины.
* после филета возможны самопересечения; `validate` может это обнаружить.

## 5.8. Densify

Цель — достаточная плотность для экспорта/визуализации без изменения формы.

Правила вставки на сегменте `(p_i, p_{i+1})`:

* по длине: `n_len = ceil(len / max_spacing_mm)`;
* по углу между соседними сегментами: если угол больше `max_angle_step_deg`,
  добавить промежуточные точки (для дуг это эквивалентно ограничению шага);
* по допуску хорды для дуги радиуса `r`: максимальная длина хорды

```text
chord_max = 2 * sqrt(max(0, 2 * r * tol - tol²))
```

где `tol = chord_tolerance_mm`. Если радиус неизвестен, использовать
`max_spacing_mm`.

Итог: `n = max(n_len, n_angle, n_chord)`, вставить `n-1` равномерных точек.
Дубликаты не добавлять. Сложность `O(n + m)`.

## 5.9. Limit curvature

Итеративное ограничение кривизны:

1. Оценить дискретную кривизну в каждой вершине:

```text
k_i ≈ 2 * cross(p_i - p_{i-1}, p_{i+1} - p_i)
      / (|a| * |b| * |a + b|)
```

(или через описанную окружность: `k = 4A / (abc)`).
`R_i = 1 / k_i`.

2. Если `R_i >= min_bend_radius_mm` для всех — готово.
3. Иначе выполнить ограниченное сглаживание в окрестности нарушителей
   (Laplacian с якорями), пересчитать кривизну.
4. Максимум итераций (например, 20). Если не сошлось — `WARNING` с указанием
   худшей вершины; в `strict` — `ERROR`.

Метод не гарантирует глобального оптимума, но достаточен для «сгладить острые
места». Важно не двигать якоря и не менять топологию.

## 5.9.1. Optimize curve (глобальный МНК)

`optimize_curve` — перенос метода из прототипа-блокнота: не последовательность
эвристик, а одна задача наименьших квадратов по всему контуру. В Blender-аддоне
это основной путь (включён по умолчанию): пока он активен, `fillet_corners`,
`cut_thin_sections`, `trim_tight_corners`, `smooth_curve_approx` и
`limit_curvature` в запрос не попадают — они решали бы ту же задачу локально и
мешали бы глобальной подгонке. Их настройки остались в закрытой панели
`Legacy shaping` для режима без оптимизатора.

```text
cost = 1/2 * Σ [ w_data   * |p_i - base_i|^2
              + w_smooth * |p_{i-1} - 2p_i + p_{i+1}|^2
              + w_radius * max(|θ_i| - θ_max_i, 0)^2 ]
```

* `w_data` — верность исходным точкам (детализация);
* `w_smooth` — энергия изгиба тонкого стержня (второе различие). Пользователь
  задаёт её не «весом», а **длиной сглаживания** `smooth` в мм:
  `w_smooth = w_data * (smooth / ds)^4`, где `ds` — шаг дискретизации. Длина
  означает масштаб, на котором разрешено менять данные ради более прямой кривой:
  `0` — член выключен, `2–5` мм — умеренно, `10+` мм — сильно. Раньше здесь был
  сырой вес (`smooth / ds³`), и его эффект зависел от шага в четвёртой степени:
  при `ds = 2.5` мм отношение к данным было `smooth / (data * ds⁴)`, то есть
  даже 10000 давали всего ~13× данных — ручка казалась мёртвой;
* `w_radius` — ограничение материала: радиус гиба меньше допустимого — это штраф,
  а не отказ, поэтому невозможный участок возвращается максимально близким к
  материалу, а не отбрасывается.

Особенности реализации:

* Все три веса — «на единицу длины» (умножаются на шаг `ds`), поэтому результат
  не зависит от плотности дискретизации.
* Радиусный член записан через угол поворота вершины: для трёх точек
  `R = chord / (2 sin θ)`, значит `|k| > 1/R_min` равносильно
  `|θ| > asin(chord / (2 R_min))`. Форма через угол имеет ограниченную
  производную; производная описанной окружности ведёт себя как `1/θ` и на почти
  коллинеарных вершинах превращает штраф в бесконечно жёсткую пружину.
* Стартовая точка — релаксация кривизны (`limit_curvature`) от ресемплированного
  контура: острый угол является каспом для локальной модели (сдвиг самой вершины
  внутрь *увеличивает* её поворот), поэтому шаг наименьших квадратов из сырого
  полигона не может его раскрыть. Семя лишь выбирает бассейн, результат
  определяет целевая функция.
* Решатель — Левенберг–Марквардт на ленточных нормальных уравнениях
  (полуширина 5, холецкий в ленточной форме). Одна итерация `O(n)`, SciPy не
  требуется: движок остаётся на стандартной библиотеке.

Параметры: `sample_points`, `data_weight`, `smooth`, `use_material_min_radius`,
`min_radius_mm`, `radius_weight`, `max_iterations`, `cost_tolerance`.
Отношение «отклонение / лишний поворот» ≈ `sqrt(radius_weight / data_weight)`
миллиметров на радиан — этим и управляет пользователь (в панели это строка
«Deviation per radian»).

`sample_points` — это **минимум**: дуга гиба различима только если на её радиус
приходится хотя бы пара точек, иначе угол превращается в длинную фаску. Поэтому
метод сам поднимает число точек до `perimeter / (R_min / 2)` (не выше 600, чтобы
решение оставалось интерактивным), а если и этого не хватает — выдаёт
предупреждение с рекомендуемым значением `Curve samples`. Допуск 2 %: посадка
5.999 мм при лимите 6.000 мм это успех, а не нарушение.

Метод сообщает прогресс через `MethodContext.report()` и уважает отмену
(`MethodContext.check_cancel()`), поэтому клиент может показывать живой монитор
и кнопку Cancel.

## 5.10. Local recalc

Задача из концепции: пересчитать только участок, не трогая остальное.

Выделение задаётся в запросе:

```json
{
  "method": "local_recalc",
  "params": {
    "slice_id": "s0",
    "contour_id": "s0.c0",
    "range": [4, 9],
    "blend_points": 2,
    "inner_operations": [
      {"method": "smooth", "params": {"iterations": 2}}
    ]
  }
}
```

Семантика:

* `range` — полуинтервал `[start, end)` индексов **текущей** геометрии
  контура, которая приходит в запросе. Движок stateless, поэтому адаптер обязан
  прислать актуальные точки.
* `blend_points` — сколько точек слева и справа используются как якоря и зона
  плавного перехода.
* Внутри диапазона применяются `inner_operations`; снаружи точки копируются
  без изменений.
* На границах — косинусное/линейное затухание веса правки, чтобы не было
  излома:

```text
w(t) = 0.5 * (1 - cos(π * t)),  t ∈ [0, 1]
p_out = p_in + w * (p_new - p_in)
```

* Если диапазон выходит за пределы контура или пуст — `E_PARAM`.

Почему не «ID вершины»: после глобального сглаживания/упрощения индексы
меняются. Адаптер хранит **текущий** результат и знает, какие индексы
выделены; для устойчивости можно дополнительно передать геометрические якоря
(`anchor_points`) и выбрать ближайшие. В v1 достаточно диапазона + якорей.

## 5.11. Bend check

Для `SCORE` с `fold`:

* проверить `fold.angle_deg <= material.max_bend_angle_deg`;
* проверить `fold.radius_mm >= material.min_bend_radius_mm`;
* рассчитать длину развёртки участка:

```text
BA = angle_rad * (r + k_factor * thickness_mm)
```

где `BA` — bend allowance (длина нейтральной линии в зоне гиба).
`r` — внутренний радиус; `k_factor` — из материала.
* вернуть `INFO`/`WARNING` с `BA`, `setback` и требуемой длиной полки.

Это **не** полноценный 3D-unfold. Движок проверяет 2D-линию сгиба и считает
компенсацию; построение 3D-развёртки и сборка — ответственность хоста или
будущего 3D-модуля.

## 5.12. Repair (экспериментально)

*v1: только безопасные операции.*

* удалить дубликаты и нулевые сегменты;
* закрыть разрыв, если концы ближе `close_tolerance_mm`;
* удалить «иглы» (точка, у которой оба соседа почти совпадают);
* обнаружить самопересечения (O(n²) с AABB-отсечением);
* **не** выполнять булевы операции и не «распутывать» сложные пересечения.

Самопересечение в v1 — диагностика `E_GEOM_SELF_INTERSECTION`, а не автофикс.
Автоматическое исправление требует полноценной polygon-библиотеки; это
осознанно вне стандартной библиотеки v1.

## 5.13. Final validate

Проверки:

* все точки конечны;
* `closed` не изменился без явного разрешения;
* число точек в пределах `Limits`;
* нет дубликатов ближе `min_segment_mm`;
* ориентация и вложенность согласованы;
* `min_radius >= material.min_bend_radius_mm`, если включена проверка;
* `max_turn <= material.max_bend_angle_deg` для `SCORE` (если применимо);
* самопересечения — если `check_self_intersection=true`;
* отклонение от исходника — если задан `max_source_deviation_mm`.

Результат проверки попадает в `diagnostics`; `status` зависит от политики.

## 5.14. Селекторы и цели

Порядок раскрытия:

1. `OperationSpec.target`, если задан; иначе `ProcessingRequest.targets`.
2. Фильтр по `slice_ids`/`slice_indices`.
3. Фильтр по `contour_ids`.
4. Фильтр по `roles` (например, только `cut`).
5. Фильтр по тегам (`tags_all` — все, `tags_any` — хотя бы один).
6. Если после фильтрации пусто:
   * `allow_empty_targets=true` → `INFO`, операция пропускается;
   * иначе `E_TARGET_EMPTY`.

Для `scope="slice"` селектор применяется к срезу, если выбран хотя бы один его
контур. Для `scope="bundle"` — ко всему запросу.

## 5.15. Политики ошибок

`per_slice` (по умолчанию):

```text
slice_ok = True
for stage in pipeline:
    try:
        state = stage(state)
    except DomainError as e:
        slice_ok = False
        diagnostics.append(e)
        state = original_slice_state   # откат всего среза
        break
```

`best_effort`: при ошибке этап пропускается, состояние остаётся последним
успешным, обработка продолжается. `strict`: первый `ERROR` → весь запрос
`ERROR`, частичные результаты не возвращаются (или возвращаются с
`status=error` и пустым `slices` — решается на уровне API; в v1 —
возвращаются исходные срезы с диагностикой).

## 5.16. Производительность и ограничения

| Операция | Сложность | Замечание |
| --- | --- | --- |
| normalize (дубликаты) | O(n) | один проход |
| simplify | O(n log n) средн. | итеративный, без рекурсии |
| smooth | O(n · iterations) | Chaikin быстро растёт по точкам |
| fillet | O(n) | число дуг ограничено |
| densify | O(n + m) | m — добавленные точки |
| curvature | O(n) | триплеты |
| self-intersection | O(n²) | только при включённой проверке |
| JSON | O(n) | доминирует на больших массивах |

Практические лимиты v1:

* до 256 срезов в запросе;
* до 200 000 точек на контур;
* до 1 000 000 точек суммарно;
* до 32 операций;
* проверка самопересечений — только для контуров до ~20 000 точек, иначе
  `WARNING` и пропуск проверки.

Чистый Python без numpy обрабатывает линейные этапы достаточно быстро; узкое
место — O(n²) проверки и JSON. Если понадобится ускорение, это делается
отдельным пакетом/адаптером за тем же протоколом, а не добавлением зависимости
в ядро.

## 5.17. Кеш и инвалидация

Ключ:

```text
sha256(
  canonical_json(request_without_request_id)
  + engine_version
)
```

Инвалидация в адаптере:

* изменился материал/операции/цели → новый запрос → новый ключ;
* изменился план срезов/кадр → пересобрать `Slice`, новые `frame_id`;
* изменился меш → сбросить исходные срезы и кадры;
* изменилось только выделение/активный срез → кеш результата не трогаем,
  перерисовываем preview.

Кеш хранит `ProcessingResult` и ссылку на `request_id`. При отмене устаревший
результат отбрасывается по `request_id`/поколению.
