# Требования к среде для API движка срезов

Статус: черновик для согласования. Версия 0.1, 2026-11-11.

Документ фиксирует **бизнес- и эксплуатационные требования** к конечной
среде, в которой будет подниматься HTTP API движка. Технические детали
формата запроса/ответа остаются в `docs/architecture/`; здесь — что среда
должна давать продукту и какие ограничения нельзя нарушать.

## 1. Назначение и границы

API обрабатывает **готовые 2D-сечения** в миллиметрах: нормализация,
филлеты, сглаживание, упрощение, отступы, ужимание, обрезка тесных углов,
контакты и метрики. Трёхмерная нарезка меша (триангуляция, плоскости,
цепочки сегментов) выполняется клиентом — в Blender это `adapters/blender`,
в другом хосте — его собственный слой.

Причины такого разделения:

* движок не зависит от `bpy` и работает в обычном Python;
* клиент владеет геометрией и не отправляет весь меш по сети;
* API остаётся детерминированным и легко тестируемым.

API **не** должен:

* импортировать Blender, `bpy`, `mathutils`;
* хранить состояние между запросами как обязательное условие работы;
* выполнять длительные фоновые задачи без отдельного согласованного
  механизма очередей.

## 2. Потребители и сценарии

| Потребитель | Сценарий | Критичность |
| --- | --- | --- |
| Blender-аддон | `validate` перед запуском, `process` пакета срезов | высокая |
| CLI и скрипты автоматизации | пакетная обработка, CI-проверки рецептов | средняя |
| Веб/CAM-интеграция | обработка контуров, получение отчёта и метрик | средняя |

Основные сценарии:

1. Проверить запрос и вернуть структурированные диагностики без обработки.
2. Обработать от 1 до 512 срезов за один запрос.
3. Вернуть результат по каждому срезу, включая срезы с ошибками
   (политики `strict`, `per_slice`, `best_effort`).
4. Отдать описание методов и их параметров (`describe`) для UI и
   валидации на клиенте.
5. Обеспечить одинаковый результат при повторном запросе с теми же
   входными данными.

## 3. Функциональные требования

| ID | Требование | Приоритет |
| --- | --- | --- |
| F1 | API принимает и возвращает JSON-конверт движка (`ProcessingRequest` / `ProcessingResult`) с версией схемы | must |
| F2 | `validate` не меняет геометрию и возвращает ошибки/предупреждения с кодом, стадией и идентификаторами среза/контура | must |
| F3 | `process` детерминирован: одинаковый запрос даёт побайтно одинаковый результат | must |
| F4 | Ошибка одного среза не ломает остальные при политике `per_slice`/`best_effort` | must |
| F5 | Лимиты запроса проверяются до обработки: число срезов, точек, размер тела | must |
| F6 | Доступны все зарегистрированные методы, их параметры и значения по умолчанию через `describe` | must |
| F7 | Автоматический равномерный шаг: при `auto_spacing` клиент/API рассчитывает `spacing = протяжённость модели вдоль оси / count`; ручной `spacing_mm` игнорируется | must (в аддоне реализовано) |
| F8 | Локализация не является обязанностью API: тексты диагностик — стабильные английские msgid, перевод — на клиенте | should |
| F9 | Метаданные результата содержат эффективный шаг, число точек, радиусы и отклонения для отчёта | should |
| F10 | Долгая обработка (> таймаута) либо отклоняется с понятной ошибкой, либо уходит в согласованную очередь | could |

### 3.1. Автоматический шаг (F7)

Правило: `count` срезов распределяются равномерно по габариту модели вдоль
выбранной оси; расстояние между соседними срезами одинаковое, по краям —
половина шага. При `count = 1` срез проходит через центр габарита.

Формула: `spacing_mm = extent_mm / count`, где `extent_mm` — разница
проекций вершин меша на нормаль плоскости. Ручной шаг при этом не
используется, но сохраняется в настройках, чтобы вернуться к нему без
потери значения. Радиальный режим не использует шаг.

## 4. Требования к среде выполнения

| Параметр | Требование |
| --- | --- |
| ОС | Linux x86_64 (контейнер), без графической подсистемы |
| Python | 3.11+; зависимости только из `requirements`/lock-файла |
| Blender | не требуется и не устанавливается |
| Процесс | stateless HTTP-воркер; горизонтальное масштабирование |
| Протокол | HTTPS, JSON UTF-8, HTTP/1.1 и HTTP/2 |
| Память | минимум 512 МБ на воркер; пиковое потребление ограничено лимитами запроса |
| CPU | 1–2 vCPU на воркер; параллелизм запросов настраивается |
| Диск | только временный; постоянное хранение не требуется |
| Время старта | до 10 секунд до готовности принимать трафик |
| Health | `/health` (процесс жив) и `/ready` (готов принимать запросы) |

Целевые показатели (уточнить по нагрузке):

* p95 `validate` — до 200 мс для типового пакета;
* p95 `process` — до 2 с для 100 срезов / 100 тыс. точек;
* ошибки 5xx — менее 0.5% запросов;
* доступность — 99.5% в месяц для production.

## 5. Данные и хранение

* По умолчанию API **не хранит** входную геометрию и результаты: запрос
  обрабатывается в памяти и забывается после ответа.
* Логи не должны содержать полные координаты контуров и имена деталей,
  если это не согласовано отдельно; достаточно `request_id`, размеров,
  кодов ошибок и таймингов.
* Если появится история/рецепты, для них нужна отдельная БД (PostgreSQL
  или объектное хранилище), срок хранения и политика удаления.
* Резервное копирование требуется только для постоянных данных, не для
  эфемерных запросов.

## 6. Безопасность

* TLS обязателен; HTTP без TLS — только внутри доверенной сети.
* Аутентификация: API-ключ или OIDC-токен (выбор — открытый вопрос).
* Ограничение размера тела запроса и числа элементов до парсинга.
* Изоляция воркеров; никакого выполнения пользовательского кода.
* Зависимости фиксируются и проверяются на уязвимости в CI.
* Секреты — только через переменные окружения/secret store, не в образе.

## 7. Наблюдаемость

* Структурированные JSON-логи с `request_id`, длительностью, числом
  срезов/точек и статусом.
* Метрики: RPS, p50/p95/p99, ошибки по кодам, использование памяти,
  размер очереди (если появится).
* Трассировка по `request_id` от входа до ответа.
* Алерты: рост 5xx, превышение p95, падение `/ready`.

## 8. Версионирование и совместимость

* Версия API в пути (`/v1/...`) и версия схемы в конверте.
* Новые необязательные поля допустимы; удаление/переименование полей —
  только в новой мажорной версии.
* `describe` возвращает версии методов, чтобы клиент мог проверить
  совместимость до отправки геометрии.

## 9. Ограничения и риски

* Без клиентской триангуляции API не умеет резать 3D-меш; это осознанное
  ограничение, а не временное.
* Экстремально плотные контуры (сотни тысяч точек) упираются в лимиты и
  таймауты; нужна деградация с понятной диагностикой, а не OOM.
* Самопересечения и вырожденная геометрия — ответственность клиента;
  API сообщает коды, но не «лечит» молча.
* Автошаг зависит от габарита вдоль оси; для косой плоскости нужен
  явный нормальный вектор, иначе результат будет неверным.

## 10. Критерии приёмки

1. `process` пакета из 512 срезов с 500 тыс. точек укладывается в
   согласованный таймаут и не превышает лимит памяти.
2. Одинаковый запрос дважды даёт идентичный JSON.
3. `validate` возвращает ошибки для битого запроса, не падая и не
   обрабатывая геометрию.
4. Срез с ошибкой при `per_slice` возвращается неизменённым, остальные
   срезы обрабатываются.
5. `describe` содержит все методы, включая `trim_tight_corners` и
   `cut_thin_sections`.
6. Health/ready отвечают корректно при старте, нагрузке и остановке.
7. Логи не содержат координат контуров без отдельного согласования.
