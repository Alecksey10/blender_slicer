# 1. Логический движок (Logical Engine)

Назначение: независимая вычислительная система, которая получает геометрические данные, обрабатывает их с учётом заданных ограничений и возвращает новые геометрические данные.

Движок не должен зависеть от конкретной GUI-среды, не должен хранить значения, он живёт в виде функций, через которые клиент, согласно определённым интерфейсам, редактирует свои данные. 


### 1.1. Основные возможности

A. Curve / Material Simulation

Моделирование поведения кривых с учётом физических или заданных пользователем свойств материала.

Основные параметры:

- минимальный радиус сгиба;
- ограничения на угол сгиба;
- допустимая кривизна;
- ограничения на плавность переходов;
- дополнительные свойства материала.
- повысить плотность точек, повысить плотность на сгибах и т.д.

B. Slice Optimization

Оптимизация существующих срезов через изменение положения и распределения точек.

Возможности:
- сглаживание кривых;
- оптимизация количества точек;
- изменение плотности точек;
- устранение резких переходов;
- соблюдение ограничений материала.

C. Local Recalculation
! - непонятно, как подобные участки подавать в движок, непонятно, как выделять их в среде проектирования. 

Перерасчёт отдельных участков срезов.

Возможности:

- пересчёт выбранных точек;
- перерасчёт отдельных участков кривых;
- локальное сглаживание;
- восстановление плавных переходов между неизменёнными и изменёнными участками.

### 1.2. Входные данные

| Данные               | Назначение                                   |
| -------------------- | -------------------------------------------- |
| Slices               | Набор срезов в виде точек и контуров         |
| Slice Count          | Количество срезов                            |
| Slice Spacing        | Расстояние между срезами, если оно применимо |
| Material Config      | Параметры материала                          |
| Processing Config    | Настройки обработки                          |
| Geometry Constraints | Ограничения на изменение геометрии           |
| Processing Mode      | Тип обработки                                |

Движок не хранит никаких данных, а только их обрабатывает. Данные хранятся в окружении, из которого подаются запросы. При этом данные хранятся без совместимости со средой, но с возможностью их отобразить или через API перевычислять


### 1.3. Метод построения и обработки

1. Среда получает исходные точки среза в 3D.
2. Для каждого среза определяется собственная локальная система координат.
3. Точки переводятся в двумерное представление.
4. Информация о преобразовании сохраняется.
5. Двумерные данные передаются движку.
6. Движок выполняет обработку.
7. Возвращает новые двумерные точки.
8. Координаты восстанавливаются в исходном 3D-пространстве.

Таким образом, движок всегда работает с обычными двумерными контурами и не зависит от пространственной ориентации срезов.

### 1.4. Выходные данные

Основной формат результата:

- идентификатор среза;
- набор обработанных контуров;
- последовательность точек каждого контура;
- информация о замкнутости контура;
- диагностические данные.

Массивы точек основным форматом обмена

Возможна вспомогательная информация, которой окружение властно распоряжаться самостоятельно:
* например, чтобы различные участки различных сегментов помечались тегами (например, кривой учасок ит.д.)
    * данная информация необязательна, но может быть воспринята окружением как дополнительная, например, для подкрашиваний.

# 2. GUI Adapter / Proxy

Назначение: универсальный посредник между логическим движком и конкретной GUI-средой.
Каждый метод 

Например:
- Blender Adapter;
- Unreal Adapter;
- Qt Adapter.

Все адаптеры используют общий контракт взаимодействия с движком.

## При этом есть какой-нибудь общий Proxy
Он передаёт данные к методам, как их построить через GUI, кофнигурации к этим методам (например, количество параметров, как их визуализирвоать, их тип, ограничения и т.д.)

### 2.1. Основные возможности

A. GUI Configuration

Конфигурация построения интерфейса.

Позволяет определять:

- какие элементы интерфейса доступны;
- какие параметры отображаются;
- какие поля доступны для редактирования;
- какие действия может выполнять пользователь;
- как компоненты группируются и располагаются.

Каждая GUI-среда самостоятельно отображает интерфейс средствами своего API.

B. API Configuration

Конфигурация внутренних методов и точек взаимодействия.

Позволяет определять:

- доступные методы;
- входные параметры;
- типы данных;
- название, документацию, описание методов
- обязательные и необязательные поля;
- форматы возвращаемых результатов;
- обработчики событий.

D. Runtime State

Управление временными данными в оперативной памяти.

Хранит:

- текущий проект;
- конфигурацию;
- исходные срезы;
- координатные преобразования;
- результаты обработки;
- временный кеш.

Данные могут храниться в глобальном состоянии плагина или в отдельных экземплярах контекста проекта.

### 2.2. Версионность

Нужно предусмотреть два независимых механизма версионности:

| Тип                   | Для чего нужен                                        |
| --------------------- | ----------------------------------------------------- |
| Host API Version      | Совместимость с версиями Blender, Unreal, Qt и их API |
| Core Protocol Version | Совместимость адаптера с логическим движком           |

Дополнительно можно версионировать схему конфигурации GUI.

Это позволит изменять интерфейс и адаптеры, не затрагивая вычислительную часть.

# 3. Общий Data Contract

Между движком и адаптерами необходим единый формат обмена данными.

Я бы выделил четыре основные сущности:

| Сущность            | Назначение                                  |
| ------------------- | ------------------------------------------- |
| `Project`           | Конфигурация и состояние проекта            |
| `Slice`             | Исходная геометрия одного среза             |
| `ProcessingRequest` | Запрос на обработку среза или группы срезов |
| `ProcessingResult`  | Возвращённая обработанная геометрия         |

Отдельно необходима сущность `CoordinateFrame`, которая хранит правила преобразования между 2D и 3D.

Таким образом, движок не должен знать, из какого приложения пришли данные, а адаптер — каким именно алгоритмом движок их обработал.

Но бекенд не знает о 3D, он работает только в двухмерной плоскости, к нему приходят либо двухмерные координаты, либо трёхмерные с занулённой третьей. 

# 4. Общий Pipeline

1\. HOST ENVIRONMENT

Blender / Unreal / Qt

Создание или загрузка Mesh

2\. HOST SLICING

Создание плоскостей и пересечение Mesh

Получение 3D-точек срезов

3\. GUI ADAPTER / DATA PREPARATION

Подготовка данных и координатных систем

Преобразование 3D → 2D

4\. LOGICAL ENGINE

Симуляция материала, оптимизация, перерасчёт

Генерация новых точек и кривых

5\. GUI ADAPTER / RESULT PROCESSING

Проверка результатов и преобразование 2D → 3D

6\. HOST VISUALIZATION

Отображение сглаженных срезов в среде

7\. EXPORT

Печать / SVG / DXF / передача в другую программу

# 5. Итоговое разделение ответственности

Я бы пока остановился на следующем наборе общих компонентов:

| № | Компонент                | Основная ответственность                        |
| - | ------------------------ | ----------------------------------------------- |
| 1 | Logical Engine           | Геометрические алгоритмы и симуляция материалов |
| 2 | GUI Adapter              | Связь с конкретной GUI-средой                   |
| 3 | GUI Configuration        | Конфигурация и построение интерфейса            |
| 4 | Host API Proxy           | Унификация методов работы с окружением          |
| 5 | Data Manager             | Единые форматы и управление данными             |
| 6 | Coordinate Manager       | Преобразования 2D ↔ 3D                          |
| 7 | Runtime / Memory Manager | Хранение состояния и кеширование                |
| 8 | Visualization Adapter    | Отображение результатов средствами среды        |
| 9 | Export Manager           | Сохранение и передача результатов               |
